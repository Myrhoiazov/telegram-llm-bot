# Понимание архитектуры ManBot

Этот файл - учебная карта проекта. Его цель - помочь понять не только что делает ManBot, но и как мыслить, чтобы в дальнейшем создавать свои похожие проекты и код.

## Главная идея

ManBot - это не просто Telegram-бот и не один файл, который отправляет сообщение в LLM и возвращает ответ.

Это локальная многоагентная AI-платформа, где пользовательская задача проходит через несколько независимых слоев:

```text
Telegram
  -> Telegram Adapter
  -> Core Orchestrator
  -> Planner Agent
  -> Task Memory
  -> Executor Agent
  -> Services / Tools / RAG / LLM / Cron
  -> Critic Agent, optional
  -> Telegram Response
```

Обычный бот часто работает так:

```text
user message -> LLM -> answer
```

ManBot работает иначе:

```text
user message
-> понять задачу
-> создать план
-> сохранить задачу в память
-> выполнить план по шагам
-> использовать инструменты при необходимости
-> проверить результат
-> вернуть ответ
```

Главный вывод: LLM здесь не вся программа. LLM - это один из сервисов внутри системы. Вокруг нее построена инфраструктура: память, маршрутизация моделей, инструменты, расписания, обработка файлов, логирование и управление процессами.

## Основные части проекта

### Core Orchestrator

Файл:

```text
src/core/orchestrator.ts
```

Это центр управления. Его можно понимать как дирижера всей системы.

Он:

- запускает остальные процессы;
- читает сообщения от них;
- пересылает сообщения по адресу `to`;
- принимает задачи от Telegram;
- вызывает Planner;
- сохраняет задачу;
- запускает Executor;
- отправляет ответ обратно.

Orchestrator - сердце проекта.

### Telegram Adapter

Файл:

```text
src/adapters/telegram-adapter.ts
```

Это внешний вход в систему.

Он:

- подключается к Telegram Bot API;
- принимает сообщения пользователя;
- обрабатывает команды `/start`, `/task`, `/new`, `/help`;
- скачивает файлы;
- создает внутреннее сообщение `task.create`;
- получает `telegram.send` и отправляет ответ пользователю.

Важно: Telegram Adapter сам не решает задачи. Он только переводит Telegram-события во внутренний протокол проекта.

### Message Protocol

Файл:

```text
src/shared/protocol.ts
```

Это общий язык всех процессов.

Каждое сообщение внутри системы выглядит примерно так:

```ts
{
  id: string,
  from: string,
  to: string,
  type: string,
  payload: unknown,
  timestamp: number,
  version: "1.0"
}
```

Пример сообщения от Telegram Adapter в Core:

```text
from: telegram-adapter
to: core
type: task.create
payload: { goal: "..." }
```

Пример сообщения от Core в Planner:

```text
from: core
to: planner
type: plan.create
payload: { goal: "..." }
```

Компоненты не вызывают друг друга напрямую. Они обмениваются сообщениями. Это делает архитектуру гибкой.

### BaseProcess

Файл:

```text
src/shared/base-process.ts
```

Это базовый класс для всех процессов.

Он делает одну ключевую вещь:

```text
stdin -> прочитать JSON-строку -> проверить через Zod -> handleEnvelope()
stdout <- отправить JSON-строку
```

Каждый сервис - отдельная Node.js-программа, которая общается с другими через JSONL: один JSON на одну строку.

Это дает:

- изоляцию процессов;
- возможность перезапуска;
- понятный протокол;
- независимое тестирование;
- возможность в будущем заменить транспорт на Redis, WebSocket, NATS, gRPC и т.д.

### Planner Agent

Файл:

```text
src/agents/planner-agent.ts
```

Planner превращает цель пользователя в план.

Пользователь пишет:

```text
Найди информацию, проанализируй и сделай вывод
```

Planner должен создать граф задач, например:

```text
research -> summarize -> final_answer
```

В коде это называется Capability Graph или DAG.

DAG - directed acyclic graph, то есть направленный граф без циклов.

Примерно:

```ts
{
  nodes: [
    {
      id: "research",
      type: "tool",
      service: "tool-host",
      input: { ... }
    },
    {
      id: "answer",
      type: "generate_text",
      service: "model-router",
      input: { dependsOn: ["research"] }
    }
  ]
}
```

Смысл: некоторые шаги можно делать только после других. Некоторые независимые шаги можно выполнять параллельно.

### Graph Utils

Файл:

```text
src/shared/graph-utils.ts
```

Здесь проверяется план.

Этот слой отвечает на вопросы:

- есть ли узлы;
- нет ли циклов;
- существуют ли зависимости;
- какие узлы можно выполнить прямо сейчас;
- какие узлы ждут результатов предыдущих.

Это фундамент выполнения сложных задач.

### Executor Agent

Файл:

```text
src/agents/executor-agent.ts
```

Executor берет готовый DAG и выполняет его.

Он:

- смотрит, какие узлы готовы;
- запускает их;
- собирает результаты;
- передает результат одного узла следующему;
- может выполнять несколько независимых узлов параллельно;
- вызывает сервисы: `model-router`, `tool-host`, `rag-service`, `cron-manager`;
- в конце возвращает агрегированный ответ.

Planner говорит, что делать. Executor делает, как выполнять.

### Model Router и Generator Service

Файлы:

```text
src/services/model-router.ts
src/services/generator-service.ts
```

Это слой работы с моделями.

Идея такая:

```text
small task  -> small model
medium task -> medium model
large task  -> large model
```

В конфиге указаны модели:

```json
{
  "modelRouter": {
    "small": "qwen2.5:0.5b",
    "medium": "qwen2.5:1.5b",
    "large": "qwen2.5:7b"
  }
}
```

Проект работает через Lemonade локально, то есть модель запускается на твоей машине.

### Lemonade Adapter

Файл:

```text
src/services/lemonade-adapter.ts
```

Это адаптер к локальному LLM-серверу Lemonade.

Он скрывает детали HTTP-запросов. Остальная система не думает о том, как именно вызвать модель. Она просто использует методы вроде:

```ts
lemonade.chat(...)
lemonade.embed(...)
```

Хороший принцип: внешние API лучше прятать за адаптерами.

### Task Memory

Файл:

```text
src/services/task-memory.ts
```

Это SQLite-память задач.

Здесь хранятся:

- задачи;
- состояние выполнения;
- узлы графа;
- результаты;
- conversation id;
- история.

Это нужно, чтобы система могла помнить, что она делала, восстанавливать состояние, архивировать сессии и анализировать прошлые задачи.

### RAG Service

Файл:

```text
src/services/rag-service.ts
```

RAG означает Retrieval-Augmented Generation.

Смысл:

```text
текст -> embedding vector -> SQLite
запрос -> embedding vector -> поиск похожих документов -> контекст для LLM
```

Проект может сохранять знания и потом находить их по смыслу, а не только по точному тексту.

Например, после `/new` старая беседа архивируется, суммаризируется и кладется в RAG.

### Tool Host

Файл:

```text
src/services/tool-host.ts
```

Это место, где живут инструменты.

Сейчас там есть:

- `shell`;
- `http_get`;
- `http_search`.

Executor или agent-node может сказать:

```text
выполни shell-команду
```

или:

```text
получи страницу через браузер
```

Tool Host также ограничивает sandbox-директорию, чтобы инструменты не работали где попало.

Очень важный принцип:

```text
LLM решает, что нужно сделать.
Код реально делает действие.
```

### Cron Manager

Файл:

```text
src/services/cron-manager.ts
```

Это расписания и напоминания.

Пользователь может написать:

```text
Напомни мне завтра в 9 утра проверить почту
```

Система парсит время, создает cron-задачу, сохраняет ее в SQLite и потом отправляет напоминание.

### File Processor

Файл:

```text
src/services/file-processor.ts
```

Это обработка файлов из Telegram.

Он может:

- читать текстовые файлы;
- распознавать изображения через vision-модель;
- транскрибировать аудио через Whisper;
- длинные тексты отправлять в RAG.

То есть файл становится частью задачи.

## Как идет одна задача

Допустим пользователь пишет в Telegram:

```text
Найди информацию про X и сделай краткий отчет
```

Внутри происходит так:

1. Telegram Adapter получает сообщение.
2. Он создает внутреннее сообщение `task.create`.
3. Orchestrator принимает задачу.
4. Orchestrator просит Planner создать план через `plan.create`.
5. Planner вызывает LLM и получает DAG-план.
6. Orchestrator сохраняет задачу в Task Memory.
7. Orchestrator отправляет план Executor через `plan.execute`.
8. Executor смотрит граф и выполняет узлы.
9. Если нужен интернет или shell, Executor вызывает Tool Host.
10. Если нужна память, Executor вызывает RAG.
11. Если нужен текст, Executor вызывает Model Router / Generator.
12. Когда результат готов, Executor отвечает Core.
13. Core отправляет сообщение в Telegram Adapter.
14. Telegram Adapter отправляет ответ пользователю.

## Как думать, чтобы создавать такие проекты

Тебе нужно мыслить не как написать один скрипт, а слоями.

### 1. Входы

Сначала реши, откуда приходит пользователь или событие:

```text
Telegram
Web UI
CLI
REST API
Discord
WhatsApp
```

В этом проекте вход - Telegram.

В будущем Telegram можно заменить на веб-приложение, Discord, WhatsApp или API.

### 2. Протокол

Все части проекта должны говорить на одном языке.

Здесь это Envelope:

```text
id
from
to
type
payload
```

Когда ты строишь свои проекты, полезно сначала придумать внутренние события:

```text
user.message
task.create
plan.create
tool.execute
memory.search
response.send
```

### 3. Orchestrator

Всегда нужен центр, который знает:

- кто доступен;
- куда отправить задачу;
- кто должен ответить;
- что делать при ошибке;
- как собрать финальный результат.

В маленьком проекте это может быть один класс. В большом - отдельный процесс, как здесь.

### 4. Агенты

Агент - это не магия. Это роль + prompt + инструменты + вход/выход.

Примеры агентов:

```text
Planner: разбей задачу на шаги
Executor: выполни шаги
Critic: проверь качество
Summarizer: сожми историю
Researcher: найди информацию
Coder: измени код
```

Хороший AI-проект разделяет мышление по ролям.

### 5. Сервисы

Сервисы делают конкретную работу:

```text
LLM service
memory service
tool service
browser service
file service
cron service
logger service
```

Сервис должен быть узким. Например, RAG Service не должен отправлять сообщения в Telegram. Он должен только сохранять и искать знания.

### 6. Память

Есть разные виды памяти:

```text
краткая история беседы
память задач
семантическая память
структурированные данные
логи
```

В этом проекте:

- Task Memory хранит задачи;
- RAG хранит смысловые документы;
- Logger хранит события;
- Cron хранит расписания.

### 7. Инструменты

LLM сама по себе не умеет реально выполнить команду, скачать страницу, прочитать файл или поставить напоминание.

Поэтому ей дают tools:

```text
shell
http_get
http_search
schedule_reminder
send_file
load_skill
```

LLM принимает решение. Код выполняет действие.

## Почему проект сделан через процессы

Можно было бы сделать все в одном файле. Но здесь другая философия.

Отдельные процессы дают:

- если упал Tool Host, вся система не падает;
- можно перезапустить один сервис;
- проще логировать;
- проще масштабировать;
- проще заменить один компонент;
- можно писать сервисы на разных языках в будущем.

Минус: сложнее архитектура.

Для учебы это полезно: ты видишь, как строятся настоящие системы.

## Минимальная версия такого проекта

Если хочешь сам построить похожий проект с нуля, начни не с полной копии, а с мини-версии:

```text
1. CLI или Telegram принимает сообщение
2. Orchestrator получает task.create
3. Planner делает простой JSON-план
4. Executor выполняет 2-3 типа узлов
5. Model service вызывает LLM
6. Tool service умеет shell или http_get
7. Memory service пишет задачи в SQLite
```

Минимальная структура:

```text
src/
  core/
    orchestrator.ts
  agents/
    planner.ts
    executor.ts
  services/
    model.ts
    memory.ts
    tools.ts
  shared/
    protocol.ts
    config.ts
    graph.ts
```

Это уже будет основа своей AI-платформы.

## Что изучать в первую очередь

Рекомендуемый порядок чтения:

1. `src/shared/protocol.ts` - понять формат сообщений.
2. `src/shared/base-process.ts` - понять, как процессы читают и отправляют JSONL.
3. `src/core/orchestrator.ts` - понять, кто кем управляет.
4. `src/adapters/telegram-adapter.ts` - понять, как внешний мир входит в систему.
5. `src/agents/planner-agent.ts` - понять, как цель превращается в план.
6. `src/shared/graph-utils.ts` - понять DAG и зависимости.
7. `src/agents/executor-agent.ts` - понять выполнение плана.
8. `src/services/tool-host.ts` - понять инструменты.
9. `src/services/task-memory.ts` и `src/services/rag-service.ts` - понять память.

## Главная формула проекта

Запомни так:

```text
Adapter принимает внешний сигнал.
Orchestrator управляет системой.
Planner строит план.
Executor выполняет план.
Services делают конкретные действия.
Memory сохраняет состояние.
Critic проверяет качество.
Adapter возвращает ответ.
```

Если понять эту формулу, можно строить свои проекты: Telegram-ботов, AI-ассистентов, исследовательские агенты, локальные автоматизации, системы с памятью, планировщики задач и инструменты для работы с файлами.

## Практическое упражнение

Чтобы закрепить понимание, можно попробовать вручную пройти один сценарий:

```text
Пользователь: "Сделай краткий отчет по теме X"
```

И расписать:

```text
1. Какой Adapter принимает сообщение?
2. Какой Envelope создается?
3. Какой type у сообщения?
4. Что делает Orchestrator?
5. Какой план должен создать Planner?
6. Какие nodes будут в DAG?
7. Какие сервисы вызовет Executor?
8. Где сохранится состояние?
9. Как ответ вернется пользователю?
```

Если ты можешь ответить на эти вопросы, значит архитектура уже начала становиться твоей, а не просто чужим кодом.
